# strand — design doc

> A CLI for scaffolding, managing, and (eventually) deploying opinionated, component-based, agent-friendly coding projects.

Status: **draft v0** — written from a survey of three reference projects (`~/git/odo/email`, `~/git/personal/finances`, `~/git/personal/turns`). Read in tandem with the _Lessons learned_ section below; most decisions here are direct reactions to something that worked or didn't in those projects.

---

## 1. Vision

`strand` gives a developer (human or AI) the same starting line every time:

```
strand new myapp --with backend,web-app,db
cd myapp
strand dev
```

…and lands them in a running, typed-end-to-end monorepo with a Postgres, a backend, a frontend, a shared API contract, a docker-compose, a worktree/branch tool, and a `.claude/` directory full of skills that already know how to operate the project.

The intent is _not_ to be a framework. It is to be an opinionated **starting point** that's friendly to incremental escape: every file written is a normal file in a normal monorepo, and the CLI can be uninstalled without breaking the project.

### Principles

1. **One way to do each thing.** No "choose your ORM" wizard. Picks: Postgres + Prisma, Express, Vite + React, Next.js 15 static, Tailwind + shadcn, Zod, Docker Compose, yarn.
2. **Component-based ("strands"), not template-of-the-month.** A project is a _set of strands_ composed in a shared layout. New strand types are first-class extension points.
3. **Templates over libraries, libraries when updating matters.** Default to copying files into the user's repo. Use a published library only when in-place updates are valuable (e.g. the strand CLI itself, possibly the API contract helpers).
4. **Agent-first.** Every strand ships a `SKILL.md` set and contributes to a top-level `CLAUDE.md`. The CLI is designed to be driven by coding agents as much as by humans.
5. **Worktree-native.** Multiple agents on multiple branches should never collide on ports, DBs, or volumes. Lift the worktree/data-branch model from `odo` from day one.
6. **No setup beyond Docker.** Postgres, Redis, etc. run in Compose. The host only needs Node + Docker + git.

### Non-goals (for now)

- Deployment. We _leave room_ for it (strand-level `deploy` hooks), but the MVP stops at "runs locally in dev".
- Polyglot backends. Backend = Node + TypeScript. (iOS is native Swift, that's fine — it consumes the shared contract via codegen.)
- Multi-tenant or remote orchestration. `strand` is a local-dev CLI.

## 2. Lessons from the reference projects

Concrete patterns to lift and to _not_ lift.

### From `email/odo` — **lift heavily**

- **Worktree + data-branch separation.** Code identity (git worktree) is separate from data identity (Postgres/Redis volumes). N agents on N branches with zero collisions. → core to strand from v0.
- **Port-block allocation.** Each branch gets a 100-port block (`4000+`, `4100+`, …). Compose reads ports from env. No hard-coded ports anywhere in compose YAML. → lift wholesale.
- **Zod `ApiEndpoint` registry as the single contract.** One Zod object per endpoint; backend `serveEndpoint(app, schema, handler)`, frontend `callEndpoint(schema, input)`, iOS codegen reads the same registry. Drift is impossible. → this _is_ strand's shared library.
- **Change-aware build/test/lint.** Default to "what changed since `origin/main`"; `--all` to override. → lift later, not MVP.
- **Skills as a first-class directory.** `.claude/skills/<name>/SKILL.md`. → lift the convention; strand strands _contribute_ skills.

### From `email/odo` — **do differently**

- **CLI as npm scripts.** `email` has 50+ npm scripts in `package.json`, each a thin wrapper around a `scripts/*.ts` file. Hard to discover, no help text, no autocomplete. → strand's CLI is **code-defined subcommands** registered via a single registry. Strands contribute commands programmatically.
- **Hard-coded port ranges in code.** `BRANCH_BASE = 4000` lives in `scripts/lib/branch.ts`. → strand keeps port layout in a JSON config (per-project, overridable).
- **Compose variants merged with `-f` flags.** Multiple `docker-compose.*.yml` files, caller decides which to load. → strand uses **a single `docker-compose.yml` with Compose profiles** (`--profile backend`, `--profile worker`) generated by the active strand set.
- **Skills as prose only.** No machine-readable metadata. → strand skills have YAML frontmatter (name, description, triggers, required strands) so they can be auto-loaded and filtered.
- **Per-package installs with no workspace.** `email` runs `yarn install` per dir to avoid hoisting. → strand uses **yarn workspaces** (a single `yarn install` at root). Hoisting is fine for the small package counts in target projects; the developer-experience win is large.
- **Per-service tsconfig sprawl** (`base`, `service`, `docker`). → strand: one `tsconfig.base.json`, services extend with a 5-line override max.

### From `finances` — **lift**

- **`scripts/start.ts` runs services foreground/background with `.runtime/*.pid` and `.runtime/*.log`.** Simpler than Docker for app code; great DX. → strand runs Postgres in Docker, app code in host Node (tsx watch + Vite). Two separate concerns.
- **`yarn run-skill <name>` for executing skills with the right env.** → strand has `strand skill <name>`.
- **Tiny root-level orchestration package.** No app code at root, just orchestration. → strand layout matches.

### From `turns` — **lift**

- **React 19 + Vite + vanilla TS + Vitest is a perfectly good standalone web-app baseline.** A `web-app` strand without a backend should still produce a useful project.
- **`GAME_DESIGN.md` at root** as a single canonical product doc → strand templates include a `PRODUCT.md` placeholder.

## 3. Core concepts

### Project

A directory holding one or more strands and a `strand.json` manifest. The manifest is the _only_ file `strand` reads to know what your project is.

```json
{
  "name": "myapp",
  "strands": ["backend", "web-app", "db", "shared"],
  "ports": { "base": 4000, "block": 100 },
  "data": { "dir": "~/.strand-data/myapp" }
}
```

### Strand

A pluggable component. A strand is a directory under `strands/` (in the `strand` repo) shaped like:

```
strands/backend/
  strand.json                  # metadata, deps, ports, profiles, commands
  template/
    managed/                   # files strand owns; regenerated on add/sync
    bootstrap/                 # files strand seeds once; user owns thereafter
  integrations/                # skills that wire this strand to others
    db/SKILL.md                # runs when both `db` and this strand are active
  skills/                      # SKILL.md files copied into project's .claude/skills/
```

Strands are _additive_: `strand add web-app` writes the strand's bootstrap files (if absent), regenerates its managed files, registers compose profiles, installs its skills, and notes any new integration skills that the current strand set now activates.

Strands declare dependencies (`backend` depends on `shared`; `ios` depends on `shared`). Resolution is trivial — toposort the requested set. Cross-strand _wiring_ (e.g. backend's Prisma client setup when `db` is also present) is **not** a hard dependency — it's an integration skill, see below.

The file-tier split (managed vs bootstrap) is the load-bearing mechanism for §9 — strand can refresh its own managed files on every `add`/`sync` without risk of clobbering user work, because user-owned changes by definition only live in bootstrap files.

### Worktree

A git worktree of the project (under `~/.strand-worktrees/<project>/<name>` or similar). Each worktree gets its own ephemeral local DB for unit tests.

### Data branch

A named Postgres/Redis/etc. volume set under `~/.strand-data/<project>/branches/<branch>/`. A worktree points at a data branch via `.strand-default-branch`. Two worktrees can share a data branch (one runs, the other reads).

Distinct from git branches deliberately — you frequently want to keep your data while testing several code branches against it, or vice versa.

### Skill

A `.claude/skills/<name>/SKILL.md` with YAML frontmatter. Strands ship skills; strand itself ships top-level meta-skills (`worktree-create`, `data-branch`, etc.) that work in any strand project.

### Integration skill

A specific kind of skill: prose instructions for an agent to wire two strands together (e.g. add a Prisma client setup to `backend/src/api.ts` when `db` is active). Lives in a strand's `integrations/<other-strand>/SKILL.md`. Fires automatically when both strands are active, either at `strand new`, `strand add`, or via the explicit `strand integrate` command. Falls back to a printed checklist for human-only workflows. The full model is in §9.

### Drift

A managed file the user has edited away from what strand would currently write. Detected at `strand sync` time via on-write hash. Strand warns and skips rather than overwriting; an explicit `--force` re-applies the strand version. Bootstrap files are never compared — they're the user's by definition.

## 4. Generated project layout

A `strand new myapp --with backend,web-app,db` produces:

```
myapp/
  strand.json
  package.json            # workspaces: ["backend", "web-app", "shared"]
  tsconfig.base.json
  docker-compose.yml      # generated; profiles: db, redis, …
  .env.example
  .gitignore
  .claude/
    skills/               # populated from each strand
  shared/
    package.json
    src/
      api/
        ApiEndpoint.ts    # the contract class (template, not lib, for v0)
        routes.ts         # registry — empty stub
      index.ts
  backend/
    package.json
    src/
      api.ts              # entrypoint, registers ApiSchema endpoints
      controllers/
    prisma/schema.prisma
  web-app/
    package.json
    vite.config.ts
    src/
      main.tsx
      api/client.ts       # callEndpoint helper
  PRODUCT.md
  README.md
  CLAUDE.md               # composed from each strand's CLAUDE fragments
```

If you `strand add ios`, an `ios/` directory shows up with an Xcode project and a `scripts/generate-swift-client.ts` already wired.

If you `strand remove web-app`, files in `web-app/` go away, workspace + compose entries are cleaned, skills owned by `web-app` are removed. (Removal is best-effort and prints a manifest of what it touched. The user can `git diff` to verify.)

## 5. Initial strand catalog

| Strand    | Stack                                    | Provides                                                            | Depends on            |
| --------- | ---------------------------------------- | ------------------------------------------------------------------- | --------------------- |
| `shared`  | TS + Zod                                 | `ApiEndpoint` class, schema registry stub, shared types             | —                     |
| `backend` | Express + Prisma + Zod                   | API server, `serveEndpoint` helper, Prisma client                   | `shared`, `db` (soft) |
| `web-app` | Vite + React 19 + TS + Tailwind + shadcn | Truly-dynamic SPA, `callEndpoint` helper                            | `shared` (soft)       |
| `site`    | Next.js 15 App Router (static export)    | Marketing/blog/SEO site, can call backend via `NEXT_PUBLIC_API_URL` | `shared` (soft)       |
| `db`      | Postgres 16 in Docker Compose            | `db` service, healthcheck, Prisma migrations wiring                 | —                     |
| `ios`     | Swift + SwiftUI + Xcode                  | Native app, Swift codegen from `shared/api/routes.ts`               | `shared`              |

"Soft" dep means: if both are present, they auto-wire; if only one is, the strand still works standalone.

Future-friendly: `worker` (BullMQ + Redis), `email` (react-email), `browser-ext`, `android`. Adding one is "drop a new dir under `strands/`".

## 6. CLI architecture

The CLI is a TypeScript Node app distributed via npm (`npm i -g @andrew/strand` — name TBD) and runnable from source (`bun bin/strand.ts` or `tsx`).

### Module layout (the `strand` repo)

```
strand/
  bin/
    strand.ts                  # entrypoint: parses argv, dispatches
  src/
    cli/
      registry.ts              # command registry; strands register commands
      commands/
        new.ts                 # strand new <name>
        add.ts                 # strand add <strand>
        remove.ts              # strand remove <strand>
        list.ts                # strand list (installed + available)
        dev.ts                 # strand dev — the MVP target
        tree.ts                # worktree management (lifted from odo)
        data.ts                # data-branch management
        skill.ts               # run a skill from skills/
        doctor.ts              # check host: node, docker, git, ports
    core/
      project.ts               # load/save strand.json
      ports.ts                 # port allocator (config-driven, not const)
      compose.ts               # generate docker-compose.yml from strands
      worktree.ts              # git worktree wrappers, .strand-default-branch
      data-branch.ts           # ~/.strand-data layout, lifecycle
      runtime.ts               # .runtime/*.pid + *.log, like finances
      strands.ts               # discover, load, validate strands
      hooks.ts                 # invoke strand hooks (postAdd, preDev, …)
      logger.ts
    strand-api/                # the public surface a strand defines against
      types.ts                 # StrandManifest, StrandHook, ComposeContribution
  strands/
    backend/
    web-app/
    site/
    db/
    ios/
    shared/
  skills/                      # meta-skills shipped with the CLI itself
    worktree-create/SKILL.md
    data-branch/SKILL.md
    add-strand/SKILL.md
    …
  DESIGN.md                    # this file
  README.md
```

### Command registry

A strand can contribute commands. Example: `db` contributes `strand db migrate`, `strand db psql`, `strand db reset`. The registry knows which strands are active in the current project and only surfaces their commands.

```ts
// strands/db/hooks/commands.ts
export const commands: StrandCommand[] = [
  { name: "db migrate", run: (ctx) => ctx.exec("yarn workspace backend prisma migrate dev") },
  { name: "db psql", run: (ctx) => ctx.dockerExec("db", ["psql", "-U", ctx.env.PGUSER]) },
];
```

`strand --help` lists core + active-strand-contributed commands together. Aim for one consistent help surface, unlike `email`'s npm-script wall.

### Strand manifest shape

```json
{
  "name": "backend",
  "version": "0",
  "description": "Express + Prisma API server with Zod-typed endpoints.",
  "dependsOn": ["shared"],
  "softDependsOn": ["db"],
  "ports": [{ "name": "BACKEND_PORT", "offset": 10 }],
  "compose": {
    "profiles": ["backend"],
    "services": {
      /* compose YAML fragment, merged into root */
    }
  },
  "workspace": { "path": "backend" },
  "skills": ["add-endpoint", "run-migration"],
  "claudeFragment": "claude.md"
}
```

`strand` resolves the active set, merges compose fragments + claude fragments + skill copies on every `strand add/remove`. Re-runnable and idempotent.

### MVP scope (this milestone)

For "bootstrap a project and run it locally in dev mode," we need exactly:

1. `strand doctor` — verify node ≥ 20, docker, git, free ports.
2. `strand new <name> --with backend,web-app,db,shared` — scaffold a project from strands.
3. `strand dev` — bring up `db` (Docker), `backend` (tsx watch), `web-app` (vite). Foreground tail logs; ctrl-C tears down.
4. `strand stop` — stop everything.
5. The four strands above (`shared`, `db`, `backend`, `web-app`) with working templates.

Worktree/data-branch commands, `site`, `ios`, deploy hooks, and skill execution come in subsequent milestones.

## 7. Dev workflow (the target experience)

```bash
strand new myapp --with backend,web-app,db
cd myapp
strand dev
# … iterating … add an endpoint to shared/src/api/routes.ts
# both backend and web-app pick up the type change immediately
strand stop
```

Under the hood, `strand dev`:

1. Reads `strand.json`, resolves active strands.
2. Allocates port block (default base 4000) and writes `.runtime/ports.json`.
3. Generates/refreshes `docker-compose.yml` from active strands' compose fragments.
4. Runs `docker compose up -d` for service strands (`db`).
5. Spawns `backend` (`yarn workspace backend dev`, which is `tsx --watch src/api.ts`) and `web-app` (`yarn workspace web-app dev`, which is `vite`) as host processes, writing PIDs to `.runtime/`.
6. Tails their logs interleaved with prefixes; ctrl-C kills both and stops `docker compose`.

Modeled on `finances/scripts/start.ts` but generalized over the active strand set.

## 8. The shared API contract (carry-over)

The `shared` strand ships an `ApiEndpoint` class and an empty `ApiSchema` registry. Backend and web-app strands' templates already import from `shared/api/routes.ts` and have working examples (a `/health` endpoint, say, plus one demo CRUD endpoint).

Adding an endpoint is one entry in `routes.ts`, one handler in a backend controller, one call site on the frontend. Types flow automatically.

This is _templated_, not libraried, on day one — copying ~150 lines of Zod-typed helper into the user's repo is fine and lets them edit it. If we later see real drift / duplication pain, we extract `@strand/api-contract` as a library.

## 9. Content tiers & extending projects over time

A strand project is meant to grow. The most common path: scaffold with `--with shared,backend,web-app`, work for a week, then decide you actually want a database — `strand add db`. By that point the user may have rewritten half of `backend/src/api.ts`, added their own controllers, restructured the workspace. Strand has to land the new strand cleanly without clobbering any of that.

The mechanism that makes this safe is a strict separation of strand-contributed files into tiers, plus an agent-mediated approach to the bits that genuinely need to modify user code.

### 9.1 Two file tiers

Every file a strand contributes is classified at template authoring time:

- **Managed** — strand owns it. Regenerated on every `strand add`, `strand sync`, or anything else that re-runs the strand's emit. The user can edit it, but it's the strand's file; edits are at the user's risk (see §9.4 on drift). Examples:
  - `docker-compose.yml` (generated from active strands' compose fragments)
  - `.env.example` (generated from active strands' port declarations)
  - Generated API client types (e.g. Swift codegen output for iOS)
  - Strand-shipped skills under `.claude/skills/<strand-name>/`
  - Future: a generated `tsconfig.references.json` if we ever need one
- **Bootstrap** — strand seeds it on the strand's first install in this project, then never touches it again. The user owns it from that point. Examples:
  - `backend/src/api.ts`, `backend/src/controllers/*`, `backend/prisma/schema.prisma`
  - `web-app/src/App.tsx`, `web-app/src/main.tsx`, `web-app/vite.config.ts`
  - `shared/src/api/routes.ts` (the registry; users will edit this constantly)
  - `package.json` files in workspaces (users add deps, scripts)

**Declaration is structural, not metadata.** Each strand's `template/` directory has `managed/` and `bootstrap/` subdirectories. Whatever path you put under `template/managed/<x>` becomes `<x>` in the user's project under managed semantics. Same for `bootstrap/`. No per-file flag in the manifest — the directory tells you everything.

```
strands/db/
  template/
    managed/
      docker-compose.yml.fragment    # contributes to the generated compose
      .env.example.fragment          # contributes to the generated env example
    bootstrap/
      backend/prisma/schema.prisma   # only seeded when backend is also active
```

(The `.fragment` extension is a convention for "this isn't a complete file — it gets merged with other strands' contributions to produce the actual file." Plain files in `managed/` are written as-is.)

The default tier, when in doubt, is **bootstrap** — the safer choice. A file you intended to manage but accidentally wrote as bootstrap just means it doesn't auto-refresh; a file you intended to bootstrap but accidentally wrote as managed could overwrite real work.

### 9.2 Integration skills

There's a third category of strand contribution that isn't a file at all: instructions for an agent to wire two strands together. These live in `strands/<strand>/integrations/<other-strand>/SKILL.md`.

Example: `strands/db/integrations/backend/SKILL.md` describes how to add a Prisma client setup to the backend strand's bootstrap files (`backend/src/api.ts`, `backend/package.json`). The skill is a markdown document with YAML frontmatter:

```yaml
---
name: wire-db-into-backend
description: Add Prisma client setup to a backend strand alongside the db strand.
requiresStrands: [db, backend]
---
```

Followed by prose that an agent (Claude Code, etc.) reads and executes by editing the user's _actual current_ `backend/src/api.ts`, not a hypothetical template. The agent reads the file, figures out where the imports go, where the client should be initialized, what existing structure to respect, and makes a targeted edit.

**When integration skills fire:**

- **`strand new --with X,Y,Z`** — after all strands' files are written, strand lists every integration skill whose `requiresStrands` is satisfied by the active set and runs them in order.
- **`strand add X`** — same, but only for integrations newly satisfied by adding `X`.
- **`strand integrate`** — explicit re-run; useful if the user just adopted strand mid-project or skipped the integration step earlier.

**Agent-vs-human fallback.** If a coding agent is in the loop, the integration runs end-to-end. If not (a human typing in a terminal), strand prints a numbered checklist of the pending integration skills with their descriptions and file paths, leaving execution to the human. This is "not delightful" but workable — strand is explicitly agent-first (see §10 decisions).

### 9.3 Lifecycle commands

The tier model implies a small command surface:

- `strand add <strand>` — add a strand to the project. Writes its bootstrap files (if absent), regenerates managed files, runs newly-applicable integrations.
- `strand remove <strand>` — remove a strand. Deletes its bootstrap files _only if untouched since seed_ (hash-checked); otherwise warns. Always regenerates managed files. Optionally lists "un-integration" skills the user may want to run by hand.
- `strand sync` — re-emit all managed files from the current strand set. Safe to run any time; the typical reason is to refresh after editing `strand.json` directly, or after upgrading the strand CLI to a version with revised templates.
- `strand integrate [skill]` — re-run pending integration skills, or a specific one. No-op if all integrations are satisfied (tracked in `.strand-local.json`).

### 9.4 Drift detection

When strand writes a managed file, it records the file's hash in `.strand-local.json`. On any later regeneration:

- If the on-disk file's hash matches what strand last wrote → safe to overwrite, no diff.
- If the on-disk hash differs → the user (or some other process) modified the file. Strand warns:
  ```
  ! managed file `docker-compose.yml` has been edited since last sync.
    Skipped. Re-run with `--force` to overwrite, or move your edits
    into a strand contribution if they belong there.
  ```

Strand never silently overwrites a drifted file. Bootstrap files have no hashing — they're explicitly the user's territory.

A future option (not v0.2): record both the seeded hash _and_ the current hash on every sync, so an "I overwrote that drift on purpose" doesn't perpetually re-warn. Defer until users actually trip on it.

### 9.5 What we explicitly are not doing

Three alternatives we considered and rejected:

- **Sentinel markers in source code** (`// strand:db:start` / `// strand:db:end`). Brittle, ugly, composes poorly across strands editing the same region, users delete them.
- **AST codemods** (jscodeshift / ts-morph per integration). Heavy to maintain, breaks on unanticipated user patterns, doesn't generalize across languages.
- **Three-way merge** against a snapshot of the original template render (Copier-style). Real conflict resolution UI to build; conflicts still hit the user; over-engineered for the agent-first case.

The agent doing the editing is already the smartest entity in the loop about reading and modifying user code. We defer to it for the modifying parts and never try to outsmart it from inside the CLI.

### 9.6 What this means for current strands

The four shipped strands (`shared`, `db`, `backend`, `web-app`) were authored before this model was formalized. Before v0.2 implementation, each needs a tier-classification pass:

- Most existing template files are **bootstrap** (api.ts, App.tsx, prisma/schema.prisma when we add it, eslint configs, tsconfigs, package.json files).
- A small number become **managed** (currently `docker-compose.yml` is already implicitly managed by being regenerated each `strand dev`; `.env.example` will join it).
- One integration skill needs to exist before db's value lands fully: `db ↔ backend` Prisma wiring.

This reclassification is part of the v0.2 milestone, not a separate step.

## 10. Decisions (locked)

1. **Yarn classic (1.x) + workspaces.**
2. **CLI distribution:** published to npm as `@<handle>/strand` (bare `strand` is squatted by an abandoned 0.0.1 package). Also runnable from clone via `bun bin/strand.ts`. During strand's own development, integration tests invoke `bun /path/to/strand/bin/strand.ts` directly — no `yarn link`, no global install. Bun-compiled binaries deferred.
3. **`strand.json` at project root**, versioned, carries `"version": "0"` from day one. Worktree-local state (active data branch, port overrides) in `.strand-local.json`, gitignored.
4. **Single `docker-compose.yml` with Compose profiles**, generated from active strands.
5. **Skills:** `SKILL.md` with YAML frontmatter (`name, description, triggers[], requiresStrands[]`).
6. **Templating:** tiny custom token replacer (`{{projectName}}`, `{{strandName}}`) over raw files. No Handlebars/EJS.
7. **Node 22 LTS.** Drop older.
8. **`strand dev` is foreground.** Background mode (`start`/`stop`/`logs`) lands in v0.1 with worktrees.
9. **Port conflicts fail fast** with a clear error, don't auto-bump.
   9b. **Default port base is hash-derived** from project name into 30000–49999 in 100-port blocks (200 distinct slots). Deterministic per name, avoids the email-project range (4000s) and all common dev defaults (3000, 5173, 8080). Pinned into `strand.json` at `strand new` time; user can override with `--base` flag or by editing the file. `strand ports` inspects the current allocation.
10. **Templates are minimal.** A `/health` endpoint and a "hello" web-app; no demo CRUD. Examples live in the README, not in generated code.
11. **One `yarn install` per worktree.** No symlinking node_modules across worktrees.
12. **No telemetry, ever.**
13. **`strand` doesn't dogfood itself in v0** — the strand repo is a normal TS monorepo, not a strand-generated project. Revisit at v1.
14. **`strand doctor` checks:** Node ≥ 22, Docker running, git ≥ 2.30, yarn classic installed. (Port availability is checked by `strand dev` at run time against the project's actual base, not by `doctor` — a stale generic check was misleading.)
15. **Name: `strand`.** Accepting the AWS Strands Agents shadow as the lesser evil after surveying loom/rig/spoke alternatives.
16. **Content tiers are structural, not metadata.** Each strand's `template/managed/` and `template/bootstrap/` directories tell strand which files it owns vs which the user owns. No per-file flag in the manifest. Default-bootstrap if in doubt — safer to under-manage than to over-manage.
17. **Cross-strand wiring is done by integration skills, not codemods.** Each strand ships `integrations/<other-strand>/SKILL.md` documents that an agent executes against the user's actual current code. For human-only workflows, strand prints the integrations as a checklist. Agent-first is the load-bearing assumption.
18. **Managed-file drift is warned, never auto-resolved.** Strand hashes managed files on write; on later sync it warns and skips if the on-disk hash diverges. `--force` to override. Bootstrap files are not hashed — they belong to the user.

## 11. Testing & linting ethos

Non-negotiable, both in `strand` itself and in every project it generates. The email project's experience is that "tests as a thing you add later" doesn't happen — they have to be in the starting state.

### 11.1 What every generated project ships with

Every `strand new` produces a project where `yarn test` and `yarn lint` pass on the first try:

- **Test runner: Vitest** across all strands (Node + jsdom). One tool, one config style. Workspace-aware (`vitest --project backend`, etc.).
- **Lint: ESLint flat config + Prettier**, with the config **inlined per strand** (each strand template ships its own `eslint.config.js` + `.prettierrc`). No shared `tooling/eslint-config` package; the configs are short, divergence between strands (Node vs React vs Next) is real, and inlining means each strand is self-contained and editable without indirection. One root command still: `yarn lint` (check), `yarn lint:fix` (autoformat + autofix) — these fan out to the workspaces, which each run their own config.
- **Type-check** is part of lint: `yarn lint` runs `tsc --noEmit` per workspace alongside ESLint.
- **Initial tests for templated code.** Each strand's template includes at least one meaningful starter test (not a `expect(true).toBe(true)` smoke test):
  - `shared`: round-trip a sample `ApiEndpoint` schema through Zod parse, encode, decode.
  - `backend`: spin up the Express app in-process and hit `/health` with supertest.
  - `web-app`: render the root component with React Testing Library and assert a known element.
  - `db`: a Prisma client-instantiation test against a throwaway SQLite or an in-process Postgres (TBD; SQLite is simpler for v0, real Postgres in integration tests).
- **Test helpers live inside the strand that needs them** (e.g. `backend/src/test-utils/withTestServer.ts`), not in a shared `tooling/test-utils/` package. Same rationale as the inline eslint configs: self-contained, editable, no extra workspace overhead.
- **No git hooks.** Lint/format enforcement is delegated to skills (e.g. a `commit` skill that runs `yarn lint:fix` and `yarn test` before staging). Since the primary user is a coding agent operating through skills, hook-based enforcement is redundant — the skill is the workflow. Humans who want belt-and-suspenders can add husky themselves; strand doesn't ship it.
- **CI workflow file** at `.github/workflows/ci.yml` running `yarn install --frozen-lockfile && yarn lint && yarn test`.

### 11.2 CLI commands

- `strand test [strand]` — `yarn workspace <strand> test`, defaults to all (and later, with change-awareness, to changed only).
- `strand lint [strand]` / `strand lint:fix [strand]` — same shape.
- These are thin wrappers over yarn workspace commands; the value is consistent surface across projects.

### 11.3 Testing the `strand` CLI itself

Two suites, deliberately separated by speed.

**Unit suite — `yarn test:unit` (Vitest, <5s wall time, run constantly).**
Covers the pure-ish core modules:

- `core/project.ts` — load/save/validate `strand.json`.
- `core/ports.ts` — port allocator: collisions, exhaustion, AirPlay carve-out.
- `core/compose.ts` — generate `docker-compose.yml` from a strand set (snapshot tests on the YAML output).
- `core/strands.ts` — discovery, dep resolution, toposort, missing-dep errors.
- `core/worktree.ts` (later) — registry parsing, default-branch pointer.
- `cli/registry.ts` — command registration, conflict detection, help text composition.
- Template token replacer.

These run against fixtures (`test/fixtures/strands/*`) and tmpdirs, never touch Docker or git or yarn.

**Integration suite — `yarn test:integration` (slower, runs in CI + on-demand locally).**
End-to-end: actually scaffold projects, install deps, run the generated lint/test/build, and start them.

For each matrix entry, the harness:

1. Creates a tmpdir, runs `strand new <name> --with <combo>` against it.
2. Runs `yarn install` (against an offline-friendly cache; populated once in CI setup).
3. Runs `yarn lint` — must pass.
4. Runs `yarn test` — must pass (i.e. the templated starter tests pass on first generation).
5. Runs `yarn build` (where applicable) — must pass.
6. Runs `strand dev` in the background, polls health endpoints with a timeout (60s for backend, 30s for vite), then `strand stop`.
7. Asserts no stray processes, no lingering Docker containers, no leftover port allocations.

**Combo matrix (v0):**

| #   | Strands                                                     | Asserts                                           |
| --- | ----------------------------------------------------------- | ------------------------------------------------- |
| 1   | `shared, db, backend`                                       | backend boots, hits `/health`, db reachable       |
| 2   | `shared, web-app`                                           | vite serves index, root component renders         |
| 3   | `shared, db, backend, web-app`                              | full stack, web-app fetches `/health` via backend |
| 4   | `web-app` alone (no `shared`)                               | minimal SPA boots                                 |
| 5   | `shared, db, backend, web-app` then `strand remove web-app` | leaves a valid, still-passing project             |

As strands grow (`site`, `ios`, `worker`), each new strand adds at least one combo to the matrix.

**Docker handling in integration tests:**

- Tests assume Docker is available; skip with a clear message if not (so `yarn test:integration` is still runnable on a Docker-less machine, just narrower).
- Each test uses a unique project name → unique port block → unique data dir → no cross-test interference.
- Hard timeout + cleanup in `afterEach` regardless of pass/fail.

### 11.4 Roadmap implications

The MVP (`v0.0`) **must** ship:

- Working `yarn test:unit` with coverage of `project`, `ports`, `compose`, `strands`, registry, templater.
- Working `yarn test:integration` with at least matrix entries #1, #2, #3 passing on CI.
- Every templated strand's starter tests pass when scaffolded.

If these don't all pass, the milestone isn't done.

## Appendix A — naming

"strand" works on three axes: the project as a whole is _a project made of strands_; a component is _a strand_; the CLI itself is _strand_. Short, googleable enough, no npm collision in the namespace we'd use (`@<user>/strand`). Open to a rename if something better turns up.
